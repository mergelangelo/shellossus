# Project Constitution

## Preamble

`shellossus` exists to provide a full-featured, autonomous coding agent that runs out of the box on every Windows machine without external runtimes, package managers, or third-party binaries. While other coding agents require Python, Node.js, or native CLI toolchains that are often blocked on corporate desktops, Citrix/VDI sessions, and locked-down servers, `shellossus` delivers complete agentic capabilities in a single, zero-dependency PowerShell script connected to any OpenAI-compatible API.

This document defines the core architectural principles, safety guarantees, and engineering invariants of the project.

---

## Article I — Zero-Dependency Runtime

### Section 1. Native PowerShell Execution
`shellossus` must run natively on **Windows PowerShell 5.1** and PowerShell 7+. It must never require Python, Node.js, Go, Rust, WSL, Docker, or any external runtime to install or operate.

### Section 2. No External Binaries or Modules
No feature or tool may depend on external command-line utilities (`rg`, `fd`, `git`, `jq`, `curl`) or external PowerShell modules (`Install-Module`). File discovery, regex search, ignore-rule matching, diff rendering, HTTP communication, and Markdown formatting must be implemented directly in PowerShell.

### Section 3. ConstrainedLanguage Compatibility
All code paths must remain compatible with PowerShell **`ConstrainedLanguage`** mode, AppLocker, and Windows Defender Application Control (WDAC). Direct `.NET` static method calls, `Add-Type` compilation, or object methods blocked in `ConstrainedLanguage` mode must not be used when native PowerShell operators and built-in cmdlets can achieve the same result.

---

## Article II — Single-Script Distribution and Source Layout

### Section 1. Modular Source, Single-File Artifact
1. All development takes place in the modular source files under [`src/`](src/) (`Config.ps1`, `Theme.ps1`, `Tools.ps1`, `Context.ps1`, `Cli.ps1`).
2. The root [`shellossus.ps1`](shellossus.ps1) file is the standalone distribution artifact generated by [`build.ps1`](build.ps1). It must never be edited by hand and must always stay in exact sync with `src/*.ps1` (`.\build.ps1 -Check`).

### Section 2. Pure ASCII Source Files
All `.ps1` files (`src/*.ps1`, `shellossus.ps1`, `build.ps1`, `install.ps1`, `tests/*.ps1`) must contain only **7-bit ASCII** characters with normalized LF line endings. This guarantees identical parsing in Windows PowerShell 5.1 regardless of file BOM or system codepage.

### Section 3. OpenAI-Compatible API Transport
`shellossus` communicates with models via standard OpenAI-compatible `/v1/chat/completions` endpoints (cloud providers, local `Ollama`/`vLLM` servers, or internal corporate gateways) using UTF-8 file-backed HTTP requests so non-ASCII prompts and responses are never corrupted by default codepages.

---

## Article III — Workspace Isolation and Credential Protection

### Section 1. Workspace Boundary Enforcement
All file operations are strictly confined to the active workspace root. No tool may read, list, search, create, or modify files outside the workspace root, with the sole exception of read-only access to registered global `SKILL.md` files via `read_file`.

### Section 2. Reparse Point and Symlink Rejection
Before accessing any path, `shellossus` must verify the target and every ancestor directory up to the workspace root. Any path that traverses a symbolic link, NTFS junction, or reparse point (`Attributes -band 1024`) must be rejected.

### Section 3. Secret and Configuration Protection
1. `.env`, `.env.*` (except `.env.example`), and the active user configuration file (`$ConfigPath`) must never be read by `read_file`, listed by `list_files`, returned by `find_files` or `grep_files`, attached via `@file`, or modified by `write_file` or `edit_file`.
2. Configuration files must be parsed strictly as plain key-value data without evaluating PowerShell expressions (`$(...)`).
3. Child processes started by `run_command` must have `SHELLOSSUS_API_KEY` and `OPENAI_API_KEY` removed from their environment variables.

### Section 4. Ignore Rules Across Directory Hierarchies
`find_files` and `grep_files` must respect `.gitignore`, `.ignore`, and `.fdignore` rules, including wildcards (`*`, `**`, `?`), directory-only patterns, and negation (`!pattern`). When a search starts in a subdirectory, ignore files must be loaded top-down from the workspace root through all intermediate parent directories down to the target directory and its subdirectories.

## Article IV — Tool Execution, File Integrity, and Undo

### Section 1. Permission Modes
Tool availability and confirmation prompts are governed by four permission modes:
1. **`ReadOnly`**: Exposes only read-only tools (`list_files`, `read_file`, `find_files`, `grep_files`, `fetch_url`, `web_search`, and `run_agent` clamped to `ReadOnly`) and blocks all file writes and shell commands.
2. **`Ask`**: Previews changes or commands and requires explicit user confirmation (`WRITE` for file changes, `RUN` for shell commands).
3. **`AutoEdit`**: Automatically approves file creations and edits while still requiring `RUN` confirmation for `run_command`.
4. **`Auto`**: Automatically approves both file modifications and shell commands within workspace boundaries.

### Section 2. Strict Argument Validation
Tool arguments must be validated against the tool's schema before execution. Unknown parameters, missing required parameters, and mismatched types (such as a string `"false"` passed for a boolean parameter) must be rejected immediately.

### Section 3. Atomic Staged Writes and Verified Backups
1. Every `write_file` and `edit_file` operation must first write the new content to a temporary staging file, verify the staged content, confirm the target file did not change on disk during user confirmation, and create a verified backup copy before replacing the target file via `Move-Item -Force`.
2. Existing file line endings (`CRLF` or `LF`) must be preserved. `edit_file` must support exact matches, CRLF-normalized matches, line-by-line fuzzy matches (ignoring trailing whitespace, BOM, and smart quotes/dashes), and non-overlapping batch `edits[]` applied bottom-to-top.

### Section 4. Safe Multi-Step `/undo`
1. Every turn records all created and modified files on the undo stack.
2. Before `/undo` (or automatic rollback on turn failure) modifies any file on disk, a preflight check must validate the entire chain of operations for that turn in reverse order.
3. Multiple edits to the same file within a single turn (such as `write_file` followed by `edit_file`, or multiple sequential `edit_file` calls) must be verified as a continuous chain and restored to the state prior to the turn.
4. If a file was manually modified by the user after the agent's write, `/undo` must refuse to overwrite the manual changes and must keep all backup files intact so the user can resolve the conflict and retry `/undo`.

### Section 5. Isolated Shell Execution and Output Logs
`run_command` must redirect stdout and stderr directly to temporary disk files to avoid memory exhaustion, enforce a strict execution timeout (`Wait-Process` followed by process termination), and save the full untruncated output under `.shellossus/output/` whenever terminal output is truncated.

### Section 6. Subagent Delegation (`run_agent`)
1. `run_agent` supports single delegation (`prompt`), parallel read-only fan-out (`parallel[]`, 1..8 tasks), and sequential pipelines (`pipeline[]`, 1..8 steps with `{previous}` / `$PREVIOUS` substitution), with `context` set to `'clean'` (default) or `'fork'` (cloning parent conversation history up to the last valid boundary).
2. Subagents cannot recursively invoke `run_agent` (`$script:SubagentDepth` is capped at 1) and can never escalate permissions above the parent session (`ReadOnly` sessions and `recon`/`audit`/`parallel[]` subagents are strictly clamped to `ReadOnly`).
3. File writes performed by in-process subagents are recorded into the parent turn's `$script:CurrentTurnWrites` so a single `/undo` atomically reverts both parent and subagent modifications.

## Article V — Context Management, Pagination, and Session Tree

### Section 1. Lossless Pagination and Truncation Metadata
1. `read_file` enforces a per-page limit of 300 lines and 20,000 characters. When the character limit is reached before the line limit, `end_line` and `next_start_line` must be calculated from the lines actually returned so no lines are skipped between pages.
2. Single lines longer than 20,000 characters must support character-offset pagination via `start_char` and `next_start_char`.
3. `grep_files` must return explicit truncation metadata (`truncated`, `truncation_reason`, `files_scanned`, `total_files`, `next_file_offset`) whenever match or file scan limits are hit.

### Section 2. Rejection of Incomplete Model Responses
Both the main agent loop (`Invoke-AgentTurn`) and context compaction (`Invoke-AgentCompact`) must inspect `finish_reason`. Any truncated or filtered response (`finish_reason=length` or `content_filter`) must be rejected before modifying conversation state or executing tool calls.

### Section 3. Session Persistence and Valid Branch Boundaries
1. Sessions are saved atomically as workspace-scoped JSONL files containing a `session_meta` header and parent-linked message entries (`id`, `parent_id`).
2. `/resume` and `-Continue` must reject sessions from different workspaces and must synchronize the active model and reset the undo stack upon loading.
3. Switching branches (`/tree`) or forking a session (`/fork`) is permitted only at valid conversation boundaries; selecting an `assistant` entry whose `tool_calls` do not have all corresponding `role = 'tool'` results in the branch must be rejected.

### Section 4. Compaction in the Session Tree
1. Context compaction (`/compact` and automatic overflow recovery) summarizes older turns into a structured handoff (`Goal`, `Constraints & Preferences`, `Progress`, `Key Decisions`, `Next Steps`, `Critical Context`) and tracks cumulative `<read-files>` and `<modified-files>` blocks across iterative compactions.
2. Compaction cut points must never fall directly on a `role = 'tool'` message.
3. Each compaction is stored as a dedicated `compaction` entry in the session tree (`entry_type = 'compaction'`, `first_kept_entry_id`) so branch reconstruction (`Build-BranchContextMessages`), `/tree` navigation, and session resume preserve the compacted state without losing other branches.

## Article VI — Output Streams and Terminal Interface

### Section 1. Clean JSONL Mode (`-Mode json`)
In `-Mode json`, `stdout` must contain only valid JSONL event objects (`turn_start`, `message_end`, `tool_execution_start`, `tool_execution_end`, `turn_end`). All plain-text `Write-Host` UI messages, diff previews, and interactive `Read-Host` prompts must be suppressed; unapproved write or command calls in `json` mode must return `status = 'cancelled'` immediately without waiting for user input.

### Section 2. Terminal Rendering (`-Mode text`)
In interactive and text modes, output uses the 24-bit TrueColor `sainnhe/gruvbox-material` (dark medium) palette, and Markdown tables are aligned by visible character width (`Get-VisibleLength`) after stripping inline formatting and ANSI sequences.

---

## Article VII — Local Customization and Extensibility

### Section 1. Layered Context and Templates
`shellossus` builds its context locally from:
1. Default system instructions or `.shellossus/SYSTEM.md` replacement;
2. `APPEND_SYSTEM.md` additions;
3. Hierarchical `AGENTS.md` and `CLAUDE.md` files from the workspace root;
4. Local and global skills (`SKILL.md`) listed in an `<available_skills>` XML catalog and invocable via `/skill:<name>` or `read_file`;
5. Built-in (`recon`, `audit`, `craft`) and custom subagent role profiles (`.shellossus/agents/*.md` and `~/.shellossus/agents/*.md`) listed in an `<available_agents>` XML catalog and invocable via `run_agent`, `/agents`, or `/agent:<role>`;
6. Prompt templates (`.shellossus/prompts/*.md`) supporting positional, slice, and default arguments (`$1`, `$@`, `$ARGUMENTS`, `${1:-default}`, `${@:2}`) without recursive re-evaluation.

---

## Article VIII — Verification and Changes

### Section 1. Automated Verification (`smoke.ps1`)
Every code change in `src/*.ps1` must be followed by running [`build.ps1`](build.ps1) to update [`shellossus.ps1`](shellossus.ps1) and running [`tests/smoke.ps1`](tests/smoke.ps1) (`Config.Tests.ps1`, `Theme.Tests.ps1`, `Tools.Tests.ps1`, `Context.Tests.ps1`, `Cli.Tests.ps1`, and `ConstrainedLanguage.Tests.ps1`).

### Section 2. Maintaining Invariants
Any new feature or bugfix must uphold Articles I through VII and include regression coverage in [`tests/`](tests/).
